# Omni Settings

<!-- Claude Code loads this file when it reads a file in this folder. -->

Omni Settings (`programs/system/omni-settings/`) is a Python GTK4/libadwaita app over these files, imported for every user with no toggle. It builds its pages from the two `_template` files (`#--` sections, `#---` headers, trailing comments), its labels from `setup.sh`'s `apps`/`services` lists and its dropdowns from the `choices`/`userChoices`/`listChoices` that `lib/settings.nix` exports, so a new setting shows up without touching the app. Its edits replace one value's text (`src/nixfile.py`), then it runs alejandra and the `lib/settings.nix` check. `src/schema.py` holds the settings it hides (`HIDDEN`), `PAGES` (each page's sidebar section, icon and blurb, and outside the Apps section which settings it shows in which group; a setting no page names stays on its template page), page renames (`PAGE_TITLES`), moves (`MOVES`), the port lists (`PORT_LISTS`) and the settings picked from lists that `default.nix` extracts at build time from glibc, xkeyboard-config and kbd (`DATA_CHOICES`). `src/dms.py` holds `LINKS`, the DankMaterialShell settings tabs the app links to and the page each shows on, opened with `dms ipc call settings openWith <tab>` (tab ids from `dms ipc call settings tabs`; DMS always shows its full window, on that tab), and reads DMS's own settings search index so the app's search finds DMS settings; its comment names the tabs left out and why. `src/descriptions.json`, keyed by setting path, holds each row's text: a plain string is the text the row shows when expanded, or an object with `title`, `summary` (the line under the name), `note` (a caution below that), `text`, `icon` (icon names or `.desktop` ids to try) and `choices` (value to label). Keep the settings files plain data (no `let`, functions or string interpolation), or the app can't parse them.

Each user's copy edits only that user (no picker; change someone else's apps by logging in as them). For someone listed on several machines, pages with app settings start with **Change For**: this machine (the default, their `users.<name>` block here), each other machine listing them (that machine's block; saved without a rebuild, since it applies when that machine rebuilds), or all of them (their own file, with the setting cleared from every machine's block). Pages are made the first time they're shown, and Discard sets the changed rows back in place, so neither stalls the window.

Master tabs in a strip across the top of the window (`TABS`, `TAB_ICONS` and `TOP` in `src/app.py`; icons only once the window is too narrow for their names) swap the sidebar: Main holds Overview, Git, Flatpaks, Backups, People and the template pages, Packages holds Search, the Apps section titled Default Packages (`section_tab`) and the User Packages section, Niri holds Window Rules, AI holds the Cloud AI and Local AI sections (always, through `section_tab` in `build()`), and Docs holds the Guides section and the Gaming section (the Proton pages in `DOCS_GAMING`, then the game notes). Icons no installed theme has are drawn in `src/icons/` (`*-symbolic.svg`, so GTK recolours them; added to the icon theme's search path in `do_startup`), such as the Guides items' light bulb. Under niri the Niri tab also gets a Shell page (the DMS quick links the Overview shows otherwise) and the Desktop section (`section_tab` in `build()`), whose pages hold the DMS links, including `Input & Connections` for the keyboard, mouse, sound, printer and network ones.

The notes pages (`src/docs.py`, its GTK-free half in `src/docstate.py`) render the repo's `docs/guide/*.md` (in file name order, so the names are numbered) and `docs/gaming/*.md` (by title) with a small Markdown reader. A relative link opens another note's page, or any other file or folder in `open_in_editor`, with `{user}` and `{machine}` in the link replaced by the login's name and the machine; a long title splits into the sidebar item's title and subtitle (`sidebar_title`) so neither is cut off.

Git (`src/git.py`, its GTK-free half in `src/gitstate.py`) is read-only: it runs `git fetch` (no prompts; SSH in batch mode), then lists the branch, changed files, commits to push and pull, recent commits, and open pull requests from GitHub's REST API, sent with `gh auth token` when gh is signed in (60 requests an hour without). Its sidebar item carries a check while nothing waits to be pushed or pulled, then an icon and count each for changed files, commits to push and pull, and open PRs (`set_git_badges` in `src/app.py`), refreshed every minute (`_git_tick` in `src/app.py`), along with the page once it's made. `gitstate.remote` limits the fetch and the GitHub call to one every 5 minutes, or 30 seconds for the Refresh button, and hands back its last results in between from `$XDG_RUNTIME_DIR/omni-settings/git-remote.json`, which both front ends share.

Backups (`src/backups.py`, its GTK-free half in `src/backupstate.py`) runs `nixm backup`, `freetube-backup` and `zen-backup` for the apps the user has on.

Search (`src/packages.py`, its GTK-free half in `src/packagestate.py`) searches nixpkgs by name through `nix-search-tv` (on the app's PATH from `default.nix`): `print` lists the names from its weekly index of search.nixos.org's unstable channel in `~/.cache/nix-search-tv`, and `preview` fills in each shown result's details. Its Install button asks for a category (one in use, `STARTER` in `src/packagestate.py`, or a typed name; `pick_category`) and adds the name under it in the user's `userPackages` set (`{Media = ["vlc"];}`), a pending change like any other. Each switch on a Default Packages page gets a button opening the module it loads in the user's `defaultApps.textEditor` (`open_in_editor`; `default.nix` passes the `forUser` pick as `OMNI_SETTINGS_EDITOR`, so a new pick takes a rebuild), found by `backend.toggle_modules` reading the routers' `lib.optionals user.<toggle> [./file]` lines (or toggles joined by `||`) when the window builds, so it follows modules as they move. User Packages has an All page, then one sidebar item per category in use (`_package_items` in `src/app.py`), each package listed with Move (the same picker), Uninstall, and Undo for a pending removal. `userPackages` is the one `GROUPED` setting (`src/schema.py`; `grouped` in `lib/settings.nix`): read, checked and written as a whole set, and a machine's `users.<name>` block replaces the user's set rather than merging with it. Its `PAGES` entry has section `"userpkgs"`, which keeps it off the generic pages, and `programs/user-packages.nix` turns every category's names into `home.packages`, a dotted name reaching into a package set. `userPackages` belongs to the user, for what they install from Search: an app the config ships, even a bare package, gets a toggle and module under Default Packages (the `add-app` skill), never an entry in someone's `userPackages`.

People (`src/people.py`, its GTK-free half in `src/peoplestate.py`) lists who can log in, and lets an admin add someone the way `setup.sh add-user` does: it refuses a name that's invalid, reserved, a system account, already listed or blocked by something at `users/<name>` that isn't a settings folder, uses an existing `users/<name>/` as it is, makes new files with `mkdir`/`open(..., "x")` so nothing is replaced, stages the new file with git, checks the result and puts everything back on any error. The rebuild then goes to the helper as `{"rebuild": true, "newUser": name}` with the first password as stdin's first line (never an argument); after switching, the helper sets it with `chpasswd` only if the account has none yet.

The Services page ends with Running Now (`src/services.py`, its GTK-free half in `src/servicestate.py`): the state, last journal lines and a restart (polkit asks) for each unit in `UNITS` the running system has; its sidebar item shows how many are running, in the success colour (`set_services_count`).

Setting rows other than switches get a reset button while their value differs from the template's (`Setting.default`); an app switch gets one when the app's settings file stays writable (`APPS` in `src/appreset.py`: Zed, Dux Files, FreeTube), which after a warning sets each setting the config's last-written copy declares back to its value, leaves the rest of the app's file alone and keeps the old file as `.old`; and Review shows each file's line changes (`backend.render`, what `write()` would save).

Pages not from the templates also include the Proton pages (`src/proton.py`, its GTK-free half in `src/protonstate.py`): Launch Options lists launch options to copy, with the nix-vn/nix-rpgm presets read off PATH as `nixm launch-params` does, and Proton Versions lists the builds from `programs.steam.extraCompatPackages` (`OMNI_SETTINGS_COMPAT_TOOLS`, set in `default.nix`), Steam's, Heroic's and Lutris's folders, marking Steam's default from its `config.vdf`; Window Rules (`src/windowrules.py`) fills a rule from a window picked with `niri msg pick-window` or `niri msg windows`, and admins add, edit and remove rules in `wm/niri/home/core/window-rules.json`, which holds every window rule `rules.nix` sets (a rebuild applies them; `name` and `note` are page labels `rules.nix` strips). Rules that need Nix (the shared styling, the `translucent-apps.nix` list) stay in `rules.nix` and are spliced in where the JSON has `{"include": "<name>"}`, so order is kept. The page reads what niri got, plus the JSON that build used, from the copy `rules.nix` writes to `~/.config/omni-settings/niri-window-rules.json`, and lists the include and machine rules read-only under Set in Nix; Flatpaks (`src/flatpaks.py`, its GTK-free half in `src/flatpakstate.py`) holds the `flatpak.enable` switch (the one `"top"` entry in `PAGES`), and runs `flatpak` itself for the rest: updates, removing unused runtimes, repair (pkexec for the system installation) and one switch per app, which uninstalls or reinstalls it straight away and remembers switched-off apps in `~/.local/state/omni-settings/flatpaks-off.json`.

Every rebuild the app starts goes through `pkexec omni-settings-apply` (`nixos/system/user/omni-settings-helper.nix`, always imported, script `src/helper.py`), so the password prompt is DMS's polkit dialog. It asks once per window: the first run starts the helper as `{"session": true}` (`src/session.py`), and later runs reach it over a socket pair only that window holds, each one a fresh helper run with the usual checks, until the window closes or sits idle for 15 minutes. The helper builds with `nix build --log-format internal-json`, which the app reads for its progress page (`src/nixlog.py`, `src/runview.py`), compares the new system with `nix store diff-closures` (`src/closure.py`), then switches the way nh does: `switch-to-configuration test` and `boot` in a `systemd-run` unit, setting the profile in between. Mode `auto` uses `boot` instead when the new system changes a `closure.CORE` package (glibc, systemd, niri, xwayland-satellite). A line `cancel` on the helper's stdin, or stdin closing, stops the build, and nothing is switched. Mode `build` is the Preview offered by Apply, Rebuild Now and Update: it builds and compares only, the helper puts back settings it saved and the app puts back what it wrote (`preview_restore`, or the old `flake.lock`), and pending changes stay so the run page's Apply Now can follow. A failed run's log is kept in `~/.local/state/omni-settings/last-failed-run.txt` (`runview.save_failed`) for the Overview's Last Failed Run row. Update can take only the sources ticked on the Overview, locked with `nix flake update <names> --output-lock-file` (`system.partial_lock`); Clean Up's dialog estimates the space from the store paths only the deleted system versions use (`system.freed_estimate`). When a finished run leaves a different `omni-settings` build on PATH than the one running, the app offers to restart, re-executing the new build once `run()` has released its D-Bus name. Admins (wheel, with write access to the repo) write the files themselves and then ask the helper to rebuild as-is; only they can update the flake inputs (the Overview page locks the newest versions into a separate file with `nix flake update --output-lock-file`, copies it over `flake.lock` and rebuilds; Undo puts the old file back) or switch to an earlier version (the helper takes only a path that is one of the system profile's generations), or clean up old versions (`{"collectGarbage": true}`: `nh clean all` with the weekly nh clean job's arguments, which both wrappers read from `nix/nh.nix`, then `switch-to-configuration boot` so the boot menu drops deleted versions).

For anyone else the machine settings are locked (per group, so a moved user setting stays editable) and the helper does the writing: it takes the caller from `PKEXEC_UID`, accepts only `users/_template` keys outside `HIDDEN` with the template's kind of value, writes that user's file (or their `users.<name>` block in the file of a machine that lists them), runs the check, builds and switches (or only saves, when the block is another machine's), and puts the file back if any step fails. That rebuild builds the whole working tree, so an admin's saved but unapplied edits go live with it.

Files made from an older template are handled in the app rather than by hand: a **What's New** page lists template settings the user's file and their machine block both leave out (`backend.new_settings`; admins also see the machine file's) and can stage them all at the template's values, or Dismiss them (kept in `~/.local/state/omni-settings/whats-new-dismissed.json`, so only a setting added later brings the page back), and when evaluation fails on keys the templates dropped, the error page lists them (`backend.stale_settings`) and removes them, for every user on the machine when an admin runs it; for a non-admin that's `omni-settings-apply '{"clean": true}'`, which works the list out itself and touches only the caller's file and block. It needs the shared repo: a `flakePath` under `/home/` is unreadable to other users.

## QML front end (in progress, branch `omni-settings-qml`)

A Quickshell front end in `qml/` is replacing the GTK one page by page; `docs/todo/omni-settings-qml.md` has the steps and a dated Status line per part. `omni-settings --qml` execs `qs -p $share/qml/shell.qml` (`OMNI_SETTINGS_QS`, `OMNI_SETTINGS_QML`, `OMNI_SETTINGS_BACKEND` from `default.nix`). `OmniView.qml` holds the shell, navigation, pending changes, `ask()` (`ConfirmDialog.qml`), `sheet` and `startJob()`; generated pages are `SettingsPage.qml`/`SettingRow.qml`, and custom pages register in its `custom` map. Data comes from `src/api.py` (`omni-settings-backend <cmd> '<json>'`, one process per call, through `Backend.call`, or `Backend.stream` for progress lines on stderr); rebuild, update, version-switch, clean-up and apply jobs go to the `omni-settings-jobs` service (`src/jobs.py`, `Jobs.qml`). Porting a page: move its GTK-free logic into a module the GTK page and `api.py` both import (`gitstate.py`, `flatpakstate.py`, `backupstate.py`, `peoplestate.py`, `servicestate.py`, `packagestate.py`, `protonstate.py`, `docstate.py`), add `api.py` commands, write the QML page. Extras the GTK app adds to a generated page (Running Now, Open Right Now) are components `SettingsPage.qml` loads by page or group title.

Gotchas:

- QML reads a property named `on` plus a capital (`onPrimary`, `onLine`) as a signal handler, so it comes out undefined: the colours are `Theme.ink*`, `Backend.stream`'s callback is `each`.
- Tap handlers take `gesturePolicy: TapHandler.ReleaseWithinBounds`; with the default, a click that closes a dialog also reaches the row under it.
- Inside an inline component, `view: view` binds the property to itself, which is why `OmniView`'s id is `omni`. Its JS has no `Array.flatMap`.
- Each `api.py` call is a new process, so state that must outlast one (the Git fetch limit) goes in a file under `$XDG_RUNTIME_DIR/omni-settings/`.
- Don't name a property after one `Item` already has (`data`, `state`): the page fails to load.
- A `Loader` in a layout takes `Layout.preferredHeight: item ? item.implicitHeight : 0`, or the next page it loads keeps the last one's height.
- Matugen has no success colour: `Theme.success` is DMS's terminal green (`dank16` color2).
- The job service runs from the installed system, so a new or changed job kind in `jobs.py` needs a rebuild before the built package can use it.
- Testing without a rebuild: build `.#nixosConfigurations.<machine>.config.home-manager.users.<user>.omni-settings.package` and run its `bin/omni-settings --qml`. For checks without a window, run `src/api.py` with the `OMNI_SETTINGS_*` variables from the installed wrapper, and load a throwaway `qml/zz*.qml` under `QT_QPA_PLATFORM=offscreen`, saving `grabToImage` renders; delete it afterwards.
