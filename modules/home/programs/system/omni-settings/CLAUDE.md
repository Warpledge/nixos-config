# Omni Settings

<!-- Claude Code loads this file when it reads a file in this folder. -->

Omni Settings (`programs/system/omni-settings/`) is a QML app (Quickshell) over these files with a Python backend, imported for every user with no toggle. It runs as DMS's slideout panel (Mod+S) and as a window (`omni-settings`, from the launcher); `qml/CLAUDE.md` has the front end's layout. It builds its pages from the two `_template` files (`#--` sections, `#---` headers, trailing comments), its labels from `setup.sh`'s `apps`/`services` lists and its dropdowns from the `choices`/`userChoices`/`listChoices` that `lib/settings.nix` exports, so a new setting shows up without touching the app. Its edits replace one value's text (`src/nixfile.py`), then it runs alejandra and the `lib/settings.nix` check. `src/schema.py` holds the settings it hides (`HIDDEN`), `PAGES` (each page's sidebar section, icon and blurb, and outside the Apps section which settings it shows in which group; a setting no page names stays on its template page), page renames (`PAGE_TITLES`), moves (`MOVES`), the port lists (`PORT_LISTS`) and the settings picked from lists that `default.nix` extracts at build time from glibc, xkeyboard-config and kbd (`DATA_CHOICES`). `src/dms.py` holds `LINKS`, the DankMaterialShell settings tabs the app links to and the page each shows on, opened with `dms ipc call settings openWith <tab>` (tab ids from `dms ipc call settings tabs`; DMS always shows its full window, on that tab), and reads DMS's own settings search index so the app's search finds DMS settings; links marked `niri` show only under niri (`links`); its comment names the tabs left out and why. `PAIRS` there puts a second setting inside another's row (each Claude skill's model in its visibility row; `pair_up`, `flat`, `pair` in `SettingRow.qml`). `src/descriptions.json`, keyed by setting path (an `a.b.*` key adds its fields to every `a.b.<name>`), holds each row's text: a plain string is the text the row shows when expanded, or an object with `title`, `summary` (the line under the name), `note` (a caution below that), `text`, `icon` (icon names or `.desktop` ids to try) and `choices` (value to label). Keep the settings files plain data (no `let`, functions or string interpolation), or the app can't parse them.

**The app never writes `modules/`** or the `_template` files. Every setting it changes, a custom page's too, lands in a machine's or user's `settings.nix` (`backend.save` refuses any other path, `backend.settings_file`); a feature that wants shared data an app page can change keeps the shared part read-only in `modules/` and takes the changes as a user setting, as `keybinds` and `windowRules` do. Its other repo writes are `flake.lock` (Update, Pull), a new person's `users/<name>/` (Users) and git itself (Pull, the backup).

Each user's copy edits only that user (no picker; change someone else's apps by logging in as them). For someone listed on several machines, pages with app settings start with **Change For**: this machine (the default, their `users.<name>` block here), each other machine listing them (that machine's block; saved without a rebuild, since it applies when that machine rebuilds), or all of them (their own file, with the setting cleared from every machine's block).

Tabs across the top (`TABS`, `TAB_ICONS` and `TOP` in `src/api.py`, sent by `load` as `tabs` and `nav`) each hold an icon rail of pages: Maintenance (tab id `main`) holds Maintenance (page id `overview`, `OverviewPage.qml`), Updates, Git, Flatpaks and Backups, System holds Users and the This Computer and Personal sections (a section `SECTION_TAB` doesn't name lands there too), Packages holds Search, the Apps section titled Default Packages (`SECTION_TAB`) and the User Packages section, Niri holds Window Rules, Side Rail and Keybinds, Network holds Tools (`nettools`) and the `network` section (Connections, Firewall, Blocking, VPN), Security holds AppArmor (only with `/etc/omni-settings/apparmor.json`), the `security` section (SSH, Antivirus) and the Security apps page titled Apps (`PAGE_TAB`), Hardware holds Firmware, Battery (only with a battery) Run on dGPU (only with `nvidia-offload` on PATH) and CPU Scheduler (only with `scx.service`; api.py's `shows`), Gaming holds Games, Launch Options, Proton Versions, MangoHud (only with `mangohud` on PATH) and the Gaming apps page titled Apps (`PAGE_TAB` takes it off Default Packages; `MOVES` adds Sunshine and Japanese VN to it), AI holds the Cloud AI and Local AI sections, and Docs holds the Guides section and the Gaming section (the game notes). Custom pages get a line behind their header's ? (`NAV_SUBTITLES`). Under niri the Niri tab also gets a Shell page holding every DMS link, by category (`shellLinks`), except those on a Network or Security page (Connections keeps its Wi-Fi, Ethernet, VPN and status links), and the Desktop section.

What each custom page does (notes, Git, Backups, Search and User Packages, Startup and File Types, Boot, Users, Running Now, reset buttons, Proton, Window Rules, Keybinds, Flatpaks, What's New) and how jobs reach the root helper are in `src/CLAUDE.md`; grep it for the page you need.

## Keep the interface clean

A page header carries one dim line under its name: what's inside while it's collapsed (`pageSummary` in `OmniView.qml`, in yellow when something waits), else what the page is for (its description or `NAV_SUBTITLES` entry). A row, card or group heading shows its name only, no line under it; the exceptions are a row that does one thing (`ActionRow.qml`, a short line on what its button does), a page's key numbers (`Tile.qml`) and an editor sheet's header (what's edited and where it's saved). What it is shows on hovering the name's text, which then gets a dotted underline (`TitleTip.qml` inside the title `Text`; a setting's `text`, else its `summary`; `info` on `ListRow` and `Section`), kept to a sentence or two (under about 200 characters). Cautions (`note`) are a yellow triangle `Hint` whose tooltip is yellow; "Set for this computer only" keeps its own icon, and a setting someone can't change is greyed with a lock left of its name. Live alerts (a restart needed, a failed fetch, a failed run) stay visible as yellow text under the name (`alert` on `ListRow`). A status value shows large on the right (`value` on `ListRow`, shrinking to fit), a setting's value as text on the right, which wraps rather than cuts and turns primary, with a bar at the row's left edge, once it differs from the default; the name keeps its full width first. A choice of up to four shows them on the row (`Segmented.qml`). Only switches with nothing to edit lose the dropdown: a dropdown never holds text alone. Data that tells list items apart (a commit's hash and author, an app ID) can stay as `subtitle`. Every icon button has a `tip`; longer guidance belongs in `PAGE_INTROS` or a guide.

For anyone else the machine settings are locked (per group, so a moved user setting stays editable) and the helper does the writing: it takes the caller from `PKEXEC_UID`, accepts only `users/_template` keys outside `HIDDEN` with the template's kind of value, writes that user's file (or their `users.<name>` block in the file of a machine that lists them), runs the check, builds and switches (or only saves, when the block is another machine's), and puts the file back if any step fails. That rebuild builds the whole working tree, so an admin's saved but unapplied edits go live with it.

## Testing

- Testing without a rebuild: build `.#nixosConfigurations.<machine>.config.home-manager.users.<user>.omni-settings.package` and run its `bin/omni-settings`. The panel only runs inside DMS, so a change to `plugin/` takes a rebuild and `dms restart`; to compile-check it first, copy the built `OmniPanel.qml` into a scratch folder with DMS's folders symlinked beside it, and `Qt.createComponent` it from a `shell.qml` there under DMS's QML import paths (`/proc/<dms quickshell pid>/environ`) with `QT_QPA_PLATFORM=wayland`, creating nothing. For checks without a window, run `src/api.py` with the `OMNI_SETTINGS_*` variables from the installed wrapper, and load a throwaway `qml/zz*.qml` under `QT_QPA_PLATFORM=offscreen`, saving `grabToImage` renders; delete it afterwards.
- The backend wrapper (`libexec/` under the split tunnel) `--set`s `OMNI_SETTINGS_FLAKE`, so a test against a scratch copy of the settings needs its own wrapper: the installed one's lines with the variable exported after them.
