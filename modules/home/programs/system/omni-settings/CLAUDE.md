# Omni Settings

<!-- Claude Code loads this file when it reads a file in this folder. -->

Omni Settings (`programs/system/omni-settings/`) is a QML app (Quickshell) over these files with a Python backend, imported for every user with no toggle. It runs as DMS's slideout panel (Mod+S) and as a window (`omni-settings`, from the launcher); the QML front end section below has its layout. It builds its pages from the two `_template` files (`#--` sections, `#---` headers, trailing comments), its labels from `setup.sh`'s `apps`/`services` lists and its dropdowns from the `choices`/`userChoices`/`listChoices` that `lib/settings.nix` exports, so a new setting shows up without touching the app. Its edits replace one value's text (`src/nixfile.py`), then it runs alejandra and the `lib/settings.nix` check. `src/schema.py` holds the settings it hides (`HIDDEN`), `PAGES` (each page's sidebar section, icon and blurb, and outside the Apps section which settings it shows in which group; a setting no page names stays on its template page), page renames (`PAGE_TITLES`), moves (`MOVES`), the port lists (`PORT_LISTS`) and the settings picked from lists that `default.nix` extracts at build time from glibc, xkeyboard-config and kbd (`DATA_CHOICES`). `src/dms.py` holds `LINKS`, the DankMaterialShell settings tabs the app links to and the page each shows on, opened with `dms ipc call settings openWith <tab>` (tab ids from `dms ipc call settings tabs`; DMS always shows its full window, on that tab), and reads DMS's own settings search index so the app's search finds DMS settings; links marked `niri` show only under niri (`links`); its comment names the tabs left out and why. `src/descriptions.json`, keyed by setting path, holds each row's text: a plain string is the text the row shows when expanded, or an object with `title`, `summary` (the line under the name), `note` (a caution below that), `text`, `icon` (icon names or `.desktop` ids to try) and `choices` (value to label). Keep the settings files plain data (no `let`, functions or string interpolation), or the app can't parse them.

Each user's copy edits only that user (no picker; change someone else's apps by logging in as them). For someone listed on several machines, pages with app settings start with **Change For**: this machine (the default, their `users.<name>` block here), each other machine listing them (that machine's block; saved without a rebuild, since it applies when that machine rebuilds), or all of them (their own file, with the setting cleared from every machine's block).

Tabs across the top (`TABS`, `TAB_ICONS` and `TOP` in `src/api.py`, sent by `load` as `tabs` and `nav`) each hold an icon rail of pages: Main holds Overview, Git, Flatpaks, Backups, Users and the template pages, Packages holds Search, the Apps section titled Default Packages (`SECTION_TAB`) and the User Packages section, Niri holds Window Rules and Keybinds, AI holds the Cloud AI and Local AI sections, and Docs holds the Guides section and the Gaming section (the Proton pages in `DOCS_GAMING`, then the game notes). Custom pages get a short line in the page list (`NAV_SUBTITLES`). Under niri the Niri tab also gets a Shell page holding every DMS link, by category (`shellLinks`), and the Desktop section.

The notes pages (`DocPage.qml`, read by `src/docstate.py`) render the repo's `docs/guide/*.md` (in file name order, so the names are numbered) and `docs/gaming/*.md` (by title) with a small Markdown reader. A relative link opens another note's page, or any other file or folder in the user's editor (api.py's `docLink`, then `openFile` in `OmniView.qml`), with `{user}` and `{machine}` in the link replaced by the login's name and the machine.

Git (`GitPage.qml`, `src/gitstate.py`) is read-only: it runs `git fetch` (no prompts; SSH in batch mode), then lists the branch, changed files, commits to push and pull, recent commits, and open pull requests from GitHub's REST API, sent with `gh auth token` when gh is signed in (60 requests an hour without). Its page-list line counts changed files, commits to push and pull, and open PRs (`gitTag` in `OmniView.qml`, from api.py's `gitSummary` every minute). `gitstate.remote` limits the fetch and the GitHub call to one every 5 minutes, or 30 seconds for the Refresh button, and hands back its last results in between from `$XDG_RUNTIME_DIR/omni-settings/git-remote.json`, since each backend call is a new process.

Backups (`BackupsPage.qml`, `src/backupstate.py`) runs `nixm backup`, `freetube-backup` and `zen-backup` for the apps the user has on.

Search (`PackagesPage.qml`, `src/packagestate.py`) searches nixpkgs by name through `nix-search-tv` (on the backend's PATH from `default.nix`): `print` lists the names from its weekly index of search.nixos.org's unstable channel in `~/.cache/nix-search-tv`, and `preview` fills in each shown result's details. Its Install button asks for a category (one in use, `STARTER` in `src/packagestate.py`, or a typed name; `CategorySheet.qml`) and adds the name under it in the user's `userPackages` set (`{Media = ["vlc"];}`), a pending change like any other. Each switch on a Default Packages page gets a button opening the module it loads in the user's `defaultApps.textEditor` (`openFile`; `default.nix` writes the `forUser` pick into `Config.qml`, so a new pick takes a rebuild), found by `backend.toggle_modules` reading the routers' `lib.optionals user.<toggle> [./file]` lines (or toggles joined by `||`) on each `load`, so it follows modules as they move. User Packages (`UserPackagesPage.qml`) has an All page, then one page per category in use, saved or pending (`packageCategories` in `OmniView.qml`), each package listed with Move (the same picker), Uninstall, and Undo for a pending removal. `userPackages` and `keybinds` are the `GROUPED` settings (`src/schema.py`; `grouped` and `keybindProblems` in `lib/settings.nix`): read, checked and written as a whole set, and a machine's `users.<name>` block replaces the user's set rather than merging with it. Its `PAGES` entry has section `"userpkgs"`, which keeps it off the generic pages, and `programs/user-packages.nix` turns every category's names into `home.packages`, a dotted name reaching into a package set. `userPackages` belongs to the user, for what they install from Search: an app the config ships, even a bare package, gets a toggle and module under Default Packages (the `add-app` skill), never an entry in someone's `userPackages`.

Users (`PeoplePage.qml`, `src/peoplestate.py`) lists who can log in, shows the user's git name and email (the schema's `"top"` page `Users`; `TOP_PAGES` in `src/schema.py` names the custom page each `"top"` page's settings show on), and lets an admin add someone the way `setup.sh add-user` does: it refuses a name that's invalid, reserved, a system account, already listed or blocked by something at `users/<name>` that isn't a settings folder, uses an existing `users/<name>/` as it is, makes new files with `mkdir`/`open(..., "x")` so nothing is replaced, stages the new file with git, checks the result and puts everything back on any error. That's the job service's `person` job, which then sends the helper `{"rebuild": true, "newUser": name}` with the first password as stdin's first line (never an argument); after switching, the helper sets it with `chpasswd` only if the account has none yet.

The Services page ends with Running Now (`RunningNow.qml`, `src/servicestate.py`): the state, last journal lines and a restart (polkit asks) for each unit in `UNITS` the running system has; its page-list line shows how many are running (`servicesRunning`). Network & Firewall ends with Open Right Now (`OpenPorts.qml`, api.py's `ports`).

Setting rows (`SettingRow.qml`) other than switches get a reset button while their value differs from the template's (`Setting.default`); an app switch gets one when the app's settings file stays writable (`APPS` in `src/resetstate.py`, sent by `load` as `resettable` only when the config wrote its copy: Zed, Dux Files, FreeTube), which after a warning sets each setting the config's last-written copy declares back to its value, leaves the rest of the app's file alone and keeps the old file as `.old`; and Review shows each file's line changes (`backend.render`, what `write()` would save).

Pages not from the templates also include the Proton pages (`ProtonPage.qml`, `ProtonVersionsPage.qml`, `src/protonstate.py`): Launch Options lists launch options to copy, with the nix-vn/nix-rpgm presets read off PATH as `nixm launch-params` does, and Proton Versions lists the builds from `programs.steam.extraCompatPackages` (`OMNI_SETTINGS_COMPAT_TOOLS`, set in `default.nix`), Steam's, Heroic's and Lutris's folders, marking Steam's default from its `config.vdf`; Window Rules (`WindowRulesPage.qml`, `RuleEditor.qml`, `src/windowrulestate.py`) fills a rule from a window picked with `niri msg pick-window` or `niri msg windows`, and admins add, edit and remove rules in `wm/niri/home/core/window-rules.json`, which holds every window rule `rules.nix` sets (a rebuild applies them; `name`, `note` and `category` are page labels `rules.nix` strips). Rules that need Nix (the shared styling, the `translucent-apps.nix` list) stay in `rules.nix` and are spliced in where the JSON has `{"include": "<name>"}`, so order is kept. The page reads what niri got, plus the JSON that build used, from the copy `rules.nix` writes to `~/.config/omni-settings/niri-window-rules.json`, and lists the include and machine rules read-only under Set in Nix; Keybinds (`KeybindsPage.qml`, `KeybindEditor.qml`, `src/keybindstate.py`) edits the user's `keybinds` setting, a pending change like any other (section `"keybinds"` in `PAGES`, sent by `load` as `keybinds`, so non-admins save through the helper, whose `keybinds_ok` checks its shape): a config bind's key, title or on/off by id, or the user's own `custom-` binds running a command (filled from a picked window's `.desktop` file, optionally wrapped in `nirius focus-or-spawn`) or a niri action. It reads each bind's default and built state, niri's action names and the changes that build applied from the copy `wm/niri/home/core/keybinds.nix` writes to `~/.config/omni-settings/niri-keybinds.json`, flags keys two enabled binds share (the build fails on them) and keys DMS's own shortcut editor sets in `niri/dms/binds.kdl`, which win; Flatpaks (`FlatpaksPage.qml`, `src/flatpakstate.py`) holds the `flatpak.enable` switch (a `"top"` entry in `PAGES`), and runs `flatpak` from the backend for the rest (api.py's `flatpakRun`, not the job service): updates, removing unused runtimes, repair (pkexec for the system installation) and one switch per app, which uninstalls or reinstalls it straight away and remembers switched-off apps in `~/.local/state/omni-settings/flatpaks-off.json`.

Rebuild, update, version-switch, clean-up, apply and add-person jobs go to the `omni-settings-jobs` user service (`src/jobs.py`, started by `%t/omni-settings/jobs.sock`), which runs `pkexec omni-settings-apply` (`nixos/system/user/omni-settings-helper.nix`, always imported, script `src/helper.py`) once per job, so DMS's polkit dialog asks for each job and the root process ends with it. Hiding the panel or restarting DMS doesn't end a job: a front end that attaches later gets its log and progress (`Jobs.qml`), and one that ends while no front end is shown sends a silent notification. The helper builds with `nix build --log-format internal-json`, which the service reads for the run page's progress (`src/nixlog.py`, `RunSheet.qml`; `Progress.graph` draws nom's dependency graph from the plan nix prints and each planned `.drv`'s inputs, under the log while it builds and at the log's end after), compares the new system with `nix store diff-closures` (`src/closure.py`), then switches the way nh does: `switch-to-configuration test` and `boot` in a `systemd-run` unit, setting the profile in between. Mode `auto` uses `boot` instead when the new system changes a `closure.CORE` package (glibc, systemd, niri, xwayland-satellite). A line `cancel` on the helper's stdin, or stdin closing, stops the build, and nothing is switched. Mode `build` is the Preview offered by Apply, Rebuild Now and Update: it builds and compares only, the helper puts back settings it saved and the job service what it wrote (`backend.restore`, or the old `flake.lock`), and pending changes stay so the run page's Apply Now can follow. A failed run's log is kept in `~/.local/state/omni-settings/last-failed-run.txt` (`save_failed` in `src/jobs.py`) for the Overview's Last Failed Run row. Update can take only the sources ticked on the Overview, locked with `nix flake update <names> --output-lock-file` (`system.partial_lock`); Clean Up's dialog estimates the space from the store paths only the deleted system versions use (`system.freed_estimate`). Admins (wheel, with write access to the repo) write the files themselves and then ask the helper to rebuild as-is; only they can update the flake inputs (the Overview page locks the newest versions into a separate file with `nix flake update --output-lock-file`, copies it over `flake.lock` and rebuilds; Undo puts the old file back) or switch to an earlier version (the helper takes only a path that is one of the system profile's generations), or clean up old versions (`{"collectGarbage": true}`: `nh clean all` with the weekly nh clean job's arguments, which the backend wrapper and the helper read from `nix/nh.nix`, then `switch-to-configuration boot` so the boot menu drops deleted versions).

For anyone else the machine settings are locked (per group, so a moved user setting stays editable) and the helper does the writing: it takes the caller from `PKEXEC_UID`, accepts only `users/_template` keys outside `HIDDEN` with the template's kind of value, writes that user's file (or their `users.<name>` block in the file of a machine that lists them), runs the check, builds and switches (or only saves, when the block is another machine's), and puts the file back if any step fails. That rebuild builds the whole working tree, so an admin's saved but unapplied edits go live with it.

Files made from an older template are handled in the app rather than by hand: a **What's New** page lists template settings the user's file and their machine block both leave out (`backend.new_settings`; admins also see the machine file's) and can stage them all at the template's values, or Dismiss them (kept in `~/.local/state/omni-settings/whats-new-dismissed.json`, so only a setting added later brings the page back), and when evaluation fails on keys the templates dropped, the error page lists them (`backend.stale_settings`) and removes them, for every user on the machine when an admin runs it; for a non-admin that's `omni-settings-apply '{"clean": true}'`, which works the list out itself and touches only the caller's file and block. It needs the shared repo: a `flakePath` under `/home/` is unreadable to other users.

## QML front end

The front end is Quickshell QML in `qml/`; `omni-settings` is `qs -p $share/qml/shell.qml`, the window. The backend path and editor come from `Config.qml`, which `default.nix` writes from `qml/Config.qml.in` along with a `qmldir`, so the same files load in DMS's process: `plugin/` is the DMS plugin (`OmniPanel.qml`, a `DSlideout` with IPC target `omniSettings`), importing the built `qml/` by its store path. The panel stays open until Mod+S or its close button hides it. `OmniView.qml` holds the shell, navigation, pending changes, `ask()` (`ConfirmDialog.qml`), `sheet` and `startJob()`; generated pages are `SettingsPage.qml`/`SettingRow.qml`, and custom pages register in its `custom` map. Data comes from `src/api.py` (`omni-settings-backend <cmd> '<json>'`, one process per call, through `Backend.call`, or `Backend.stream` for progress lines on stderr); jobs go to the `omni-settings-jobs` service (`src/jobs.py`, `Jobs.qml`). A new custom page is a QML page in the `custom` map, `api.py` commands for its data, and its logic in a `src/*state.py` module when it's more than a few lines. Extras on a generated page (Running Now, Open Right Now) are components `SettingsPage.qml` loads by page or group title. When `omni-settings` is in the machine's `mullvad.splitTunnel`, `bin/omni-settings-backend` runs the real one in `libexec/` through `mullvad-exclude`, since the panel's backend calls come from DMS's process, which the split tunnel's PATH wrapper never sees.

Gotchas:

- QML reads a property named `on` plus a capital (`onPrimary`, `onLine`) as a signal handler, so it comes out undefined: the colours are `Theme.ink*`, `Backend.stream`'s callback is `each`.
- Tap handlers take `gesturePolicy: TapHandler.ReleaseWithinBounds`; with the default, a click that closes a dialog also reaches the row under it.
- Inside an inline component, `view: view` binds the property to itself, which is why `OmniView`'s id is `omni`. Its JS has no `Array.flatMap`.
- JSON sent back from QML loses `.0` on whole numbers and can come back with its keys sorted, so files are written from data the backend read itself (`windowrulestate.edited`, the window rules undo). A `Repeater` delegate's `modelData` is a copy: edits go through the source list by index (`RuleEditor.qml`).
- Each `api.py` call is a new process, so state that must outlast one (the Git fetch limit) goes in a file under `$XDG_RUNTIME_DIR/omni-settings/`.
- Don't name a property after one `Item` already has (`data`, `state`): the page fails to load.
- A `Loader` in a layout takes `Layout.preferredHeight: item ? item.implicitHeight : 0`, or the next page it loads keeps the last one's height.
- A `Loader` whose item wraps text (a `Text` sized by width) gets only `width` from its parent, inside an `Item` taking the item's `implicitHeight`; sizing it from a layout loops (`DocPage.qml`).
- The backend wrapper (`libexec/` under the split tunnel) `--set`s `OMNI_SETTINGS_FLAKE`, so a test against a scratch copy of the settings needs its own wrapper: the installed one's lines with the variable exported after them.
- Matugen has no success or warning colour, and its `tertiary` needn't be yellow: `Theme.success` and `Theme.caution` are DMS's terminal green and yellow (`dank16` color2 and color3). Status colours go through a `tone` on `ListRow`, `Badge` and `Chip`.
- The job service runs from the installed system, so a new or changed job kind in `jobs.py` needs a rebuild before the built package can use it. A rebuild leaves the running service alone (`X-SwitchMethod = "keep-old"`), and DMS's panel stays attached, so it exits on its own once the installed unit's `ExecStart` names another build and no job is left to show (`installed_exec_start`); the socket starts the new one on the next request.
- Testing without a rebuild: build `.#nixosConfigurations.<machine>.config.home-manager.users.<user>.omni-settings.package` and run its `bin/omni-settings`. The panel only runs inside DMS, so a change to `plugin/` takes a rebuild and `dms restart`; to compile-check it first, copy the built `OmniPanel.qml` into a scratch folder with DMS's folders symlinked beside it, and `Qt.createComponent` it from a `shell.qml` there under DMS's QML import paths (`/proc/<dms quickshell pid>/environ`) with `QT_QPA_PLATFORM=wayland`, creating nothing. For checks without a window, run `src/api.py` with the `OMNI_SETTINGS_*` variables from the installed wrapper, and load a throwaway `qml/zz*.qml` under `QT_QPA_PLATFORM=offscreen`, saving `grabToImage` renders; delete it afterwards.
